# アーキテクチャ: メタデータカタログ・補完・探索・ローカル SQL

SQL エディタの補完と、DB / Schema / Table / Column の探索 UI を、**1 つのメタデータカタログ**の上に載せる。
開いたファイルとクエリ結果への SQL（ローカル SQL）は末尾の節で扱う。
本書は部品の構成・責務・データの流れ・主要な設計判断を扱う。型と公開 API は `docs/design.md` で決める。

## 目標

- エディタで DB / スキーマ / テーブル / カラム / キーワードを補完する。数万テーブル規模のアカウントでも入力を止めない
- 起動直後から前回のキャッシュで補完が効き、裏で最新化される
- 全件を最初に取らない。必要になりそうな所から段階的・非同期に取る
- カタログを探索する UI（ツリー、ファジージャンプ、パス操作）を補完と同じデータで提供する

## 前提となる Snowflake の制約

設計判断の根拠になる外部仕様。

| 手段 | warehouse | 鮮度 | 制約 |
|---|---|---|---|
| `SHOW DATABASES / SCHEMAS / TERSE OBJECTS` | 不要 | 即時 | 1 回 10,000 件まで。超えるとエラー。`LIMIT n FROM 'name'` でページング。更新時刻の列はない |
| `SHOW COLUMNS IN …` / `DESCRIBE TABLE` | 不要 | 即時 | `SHOW COLUMNS` は 10,000 件を超えた分を**エラーなしで落とす** |
| `<db>.INFORMATION_SCHEMA.*` | 必要（課金） | 即時 | DB 単位。`TABLES.LAST_DDL` で差分を検出できる。絞り込みが甘いと "returned too much data" |
| `SNOWFLAKE.ACCOUNT_USAGE.*` | 必要（課金） | 最大数時間遅れ | アカウント全体を 1 クエリで取れる。専用の権限が要る |

- 見えるオブジェクトは **role で変わる**。キャッシュは (account, role) ごとに分ける
- `snowflake-api` は `SHOW` / `DESCRIBE` の結果を JSON rowset で返す。現状の `run_query` は JSON をエラーにしている。
  JSON の応答が chunk に分割された場合に後続を読まない実装なので、大きな `SHOW` が欠ける可能性がある（要実測）

## 部品

```
            ┌──────────── UI スレッド ────────────────────────────────┐
 key input →│ Editor ─→ ContextAnalyzer ─→ Completer ─→ Popup         │
            │                                  │  ▲                   │
            │ Explorer (Tree / Jump / Path) ───┤  │ 読む              │
            │                                  ▼  │                   │
            │                       Catalog（メモリ上の正）            │
            └───────────────┬──────────────────▲──────────────────────┘
                 FetchRequest│                  │ CatalogPatch
                            ▼                  │
                 ┌──────── MetaWorker（専用スレッド・専用セッション）──┐
                 │ 優先度キュー / 重複排除 / 世代管理                   │
                 │ MetadataSource（SHOW 系、任意で INFORMATION_SCHEMA） │
                 └───────────┬──────────────────────────────────────────┘
                             ▼
                      CacheStore（ディスク、(account, role) ごと）
```

| 部品 | 責務 | 持たない責務 |
|---|---|---|
| **Session** | Snowflake への接続を保持して再利用する。Arrow と JSON の両方の結果を返す | 何を取るかの判断 |
| **MetadataSource** | 「このスコープの子一覧をくれ」を SQL に変換し、結果をカタログの形に正規化する。ページングと 10K 上限の扱いもここ | スケジューリング |
| **MetaWorker** | FetchRequest を優先度順に処理し、CatalogPatch を UI に返す。同じキーの重複要求をまとめ、古い世代の結果を捨てる | 補完・表示 |
| **Catalog** | ノード（DB / Schema / Relation / Column）と、各ノードの**ロード状態**を持つ唯一の正。読み取りは同期で即答する | 取得 |
| **CacheStore** | Catalog をスコープ単位でディスクへ書き、起動時に読み戻す | 鮮度の判断 |
| **ContextAnalyzer** | カーソル前の SQL から「今何を補完すべきか」を求める。修飾子、FROM/JOIN のテーブル、エイリアス、CTE を抽出する。壊れた SQL でも答えを出す | カタログ参照 |
| **Completer** | 文脈とカタログから候補を集めて順位を付ける。足りないスコープは FetchRequest として要求する | 描画 |
| **Explorer** | カタログを閲覧するビュー群。ノードを開く・見えるとそのスコープを要求する | 取得 |
| **Prefetcher** | 起動時・取得完了時・入力が止まったときに、次に何を要求するかを決める（P1 と P3） | 状態、取得 |

既存の `QueryEngine`（ユーザーのクエリ）とは**ワーカーを分ける**。メタデータの取得がユーザーのクエリを待たせないようにするため。
Session は両者で同じ実装を使い、接続は別々に持つ。

## データの流れ

### ロード状態と段階

カタログの各**コンテナ**（アカウント、DB、スキーマ、テーブル）は、子一覧のロード状態を持つ。

```
NotLoaded ─→ Loading ─→ Loaded { at, source } ─→ Stale（TTL 超過・無効化）─→ Loading …
                    └─→ Failed { error, at }
```

- 「親はあるが子はまだ無い」状態を正常系として扱う。補完も Explorer も、子が無いコンテナでは「取得中」を表示する
- 取得はスコープ単位で**置き換える**（差分を当てない）。段階をまたいだ不整合（テーブル一覧とカラム一覧が別時点のもの）を起こさないため
- `Stale` のデータも返す。古い候補を即座に出し、裏で再取得する（stale-while-revalidate）

取得の段階:

| 段階 | 内容 | 既定の取得方法 |
|---|---|---|
| L1 名前 | DB・スキーマ・テーブル / ビューの名前と種別。テーブルの行数・サイズ・コメントも同じ結果に含まれる | `SHOW DATABASES` / `SHOW SCHEMAS` / `SHOW OBJECTS`（スキーマ単位でページング） |
| L2 構造 | カラム名・型・コメント | `SHOW COLUMNS IN <テーブル>` |
| L3 中身 | プレビュー行、カラムのプロファイル | 明示操作のみ。warehouse を使う |

L3 はカタログとは別ストアに置く。課金を伴い量も大きいため。キーは同じオブジェクト識別子を使う。

### 何をいつ取るか（優先度）

| 優先度 | きっかけ | 取るもの |
|---|---|---|
| P0 要求 | `db.` / `schema.` / `alias.` の入力、Explorer でノードを開く | そのスコープの子 |
| P1 文脈 | エディタの SQL に出てきたテーブル（入力が止まったとき）、current DB / schema | 参照テーブルのカラム、current schema の L1 |
| P2 可視 | Explorer で画面に見えているノード | そのノードの L1 |
| P3 巡回 | アイドル時 | DB → スキーマ → テーブル名の幅優先。件数が閾値以下のスキーマだけカラムまで取る |

- P3 は同時実行数と間隔を絞る（cloud services の負荷を抑える）
- スキーマのテーブル数を見て、カラムまで先読みするか、テーブル単位で lazy に取るかを決める
- 要求したスコープが届いたら、補完ポップアップを再計算する

### 無効化

- **TTL**: スコープごとの経過時間で `Stale` にする
- **自分の DDL**: ユーザーが実行した SQL が `CREATE / ALTER / DROP / RENAME / USE` なら、該当スコープを `Stale` にする
- **手動 refresh**: 選択中のノード、またはカタログ全体
- role の切り替えは別カタログへの切り替えとして扱う

### 補完の流れ

1. ContextAnalyzer がカーソル前のテキストから補完の文脈を作る
   - 何を補完するか（キーワード / スキーマ付き名前 / カラム …）、修飾子、入力中の接頭辞、文中のテーブル・エイリアス・CTE
   - カーソル位置にプレースホルダを挿入してから解析する（未完成の SQL でも構文として成立させるため）
2. Completer が候補を集める: カタログ（current DB / schema で修飾なしの名前を解決）、文中のエイリアス・CTE、キーワード
3. 修飾子が合わない候補を除き、ファジースコアに加点して並べる。加点: 先頭一致、文中に既出、current schema、使用頻度
4. 候補の元になるスコープが `NotLoaded` / `Stale` なら FetchRequest を出す。届いたら 2 からやり直す
5. （後回し）ローカルに無い名前を入力し続けている場合は、`SHOW … LIKE` によるサーバ検索に落とす（件数上限付き）

## 探索 UI

すべて Catalog を読むビューで、独自の状態を持たない。同じオブジェクト識別子を指す。

| 機能 | 内容 | 必要なもの |
|---|---|---|
| ツリー（Miller columns） | `DB │ Schema │ Table │ Column` を左右に移動。右端にカラム一覧・行数・サイズ | L1・L2 |
| ファジージャンプ | 全カタログから名前・コメントで飛ぶ（`Ctrl+P`） | L1（巡回済みの範囲） |
| 仮想パス | `:cd DB.SCHEMA`、`:ls`、パス補完。カレントを `USE DATABASE / SCHEMA` と同期し、補完の修飾なし名前の解決にも使う | L1 |
| カラム逆引き | 「このカラム名を持つテーブル」 | L2（巡回済みの範囲） |
| エディタ連携 | ノードの名前や `SELECT` の雛形をエディタに挿入する。エディタ上の識別子から該当ノードへ飛ぶ / 定義を覗く | L1・L2 |
| プレビュー / プロファイル | `LIMIT` 付きの先頭行、カラムの分布・null 率・distinct 数。既存の結果グリッドで表示 | L3（明示操作） |

「階層をファイルシステムとして扱う」は**データモデルではなく表現の 1 つ**にする。FUSE 等で本物の FS にはしない。
Snowflake の階層は 3 段固定で、横断検索（カラム逆引き）はパスでは表せない。FS の `stat` / `readdir` の量はそのまま課金に跳ね返る。
`rm = DROP` のような書き込みの意味付けもしない。

warehouse を使う操作は UI 上で区別して表示する（L3 だけが該当する）。

## 主要な設計判断

| 判断 | 理由 |
|---|---|
| カタログを 1 つにして、補完と探索はそれを読むだけにする | 片方で取ったメタデータがもう片方でも効く。取得とキャッシュの実装が 1 本で済む |
| 既定の取得は warehouse 不要な `SHOW` 系だけ。`INFORMATION_SCHEMA` / `ACCOUNT_USAGE` は opt-in | 補完のために warehouse を起動して課金させない |
| `SHOW … IN ACCOUNT / IN DATABASE` で一括取得しない。スキーマ単位でページングする | 10K を超えるとテーブルはエラーになり、カラムはエラーなしで欠ける |
| メタデータは専用ワーカー・専用セッションで取る | ユーザーのクエリと取得が互いを待たない |
| スコープ単位で置き換え、子の欠けを正常系にする | 段階をまたいだ不整合を構造的に起こさない |
| キャッシュは (account, role) ごと | role で可視範囲が違う |
| フル AST に依存しない文脈解析 | 補完が必要なのは書きかけの SQL を書いている間であり、そのとき SQL はほぼ常に構文として壊れている |

## 先に片付ける前提作業

補完より前に必要になる。

1. Session の再利用（現状はクエリごとにログインし直している）
2. JSON rowset の結果を扱えるようにする（`SHOW` / `DESCRIBE` に必要）。大きな `SHOW` で chunk が欠けないか実測する

## 合意済みの選択

| 項目 | 選択 | 理由 |
|---|---|---|
| CacheStore の形式 | SQLite（rusqlite） | スコープ単位で、トランザクションの中で部分的に置き換えられる |
| 取得元の既定 | `SHOW` 系のみ。`INFORMATION_SCHEMA` は設定で有効にしたときだけ | 補完のために warehouse を起動させない |
| 文脈解析 | 自前の軽量トークナイザ | Snowflake 固有の構文に依存せず、壊れた SQL に強い。足りなくなったら寛容なパーサに替える |
| P3 巡回の既定の範囲 | current DB のみ。アカウント全体は設定で広げる | 大規模アカウントで巡回が終わらない・負荷をかけるのを避ける |
| ファジーマッチ | frizbee | MIT。typo を許容し、速い |

## ローカル SQL

開いた CSV / Parquet と、表示したクエリ結果（Snowflake でもローカルでも）に、TUI の中から SQL を投げる。

### 使い方の流れ

```
データを表示（ファイル / Snowflake の結果）
   │ d（ドリルダウン）
   ▼
上にエディタが開き、`SELECT * FROM <今の表示の名前>` が入る
   │ 編集して Ctrl+R
   ▼
下の表示が結果に入れ替わる（その結果にも名前が付き、さらにドリルダウンできる）
```

- エディタは**実行先**（Snowflake / ローカル）を持つ。ドリルダウンするとローカルになり、`Ctrl+T` で切り替える。実行先はエディタの枠に出す
- Snowflake に接続していない（ファイルを開いた）ときは、実行先はローカルだけ

### 名前

| 対象 | 名前 |
|---|---|
| 開いたファイル | ファイル名から拡張子を除き、小文字にして英数字と `_` 以外を `_` にしたもの（`Sales-2024.csv` → `sales_2024`） |
| 表示した結果 | 表示した順に `result_1`, `result_2`, … |
| 直前の結果 | `last`（最新の `result_N` と同じもの） |

- ファイル名を小文字に揃えるのは、DataFusion がクォートしない識別子を小文字に正規化するため。打ったとおりの名前で引ける。
  英数字にならない名前は `file`、`last` / `result_N` と同じになる名前は `file_` を前に付ける
- 列名も同じ理由で、大文字だけの列名（Snowflake の結果の `ORDER_ID` など）は小文字にして登録する。表示は元の名前のまま。
  同じ名前の列が重なったら `_2`, `_3`, … を付ける
- 結果は表示したものをすべて登録する。ドリルダウンの起点を後から選び直せるようにするため
- ドリルダウンの初期文は `last` ではなく `result_N` を使う。`last` は実行のたびに動くので、同じ文を再実行すると前回の結果をさらに絞り込んでしまう
- 0 行の結果は登録しない（列の情報が無いため）。その間はドリルダウンできない

### 部品

| 部品 | 責務 |
|---|---|
| **LocalEngine** | DataFusion の `SessionContext` を専用スレッドで持ち、ファイル・結果の登録とクエリの実行を順に処理する。結果は RecordBatch で返す。SQL は読み取り専用（DDL・DML・SET は拒否） |
| **ResultNamer**（App 内） | 表示した結果に `result_N` を振り、LocalEngine に登録を依頼する。名前を App 側で決めるのは、登録完了を待たずにエディタの初期文に使うため |
| **LocalSource** | `MetadataSource` の実装。`SessionContext` のカタログからテーブル名を読む。warehouse も通信も要らない |
| **ローカル用 MetaSystem** | Snowflake 用とは別の Catalog を持つ。補完はエディタの実行先に応じてどちらかを使う |

```
         表示した結果 ──登録──▶ LocalEngine（DataFusion, 専用スレッド）◀──登録── 開いたファイル（表示用に読み込んだデータ）
                                   ▲  │
                      SQL（ローカル）│  │ RecordBatch / 登録完了
                                   │  ▼
 エディタ ── 実行先 ──▶ App ──────────┘──▶ 結果グリッド
             │
             └─ 補完 ─▶ ローカル用 MetaSystem ─▶ LocalSource（SessionContext のカタログを読む）
```

### 主要な設計判断

| 判断 | 理由 |
|---|---|
| エンジンは DataFusion（52.x） | arrow 57 の RecordBatch をそのまま受け渡せる（snowflake-api が arrow 57 に固定しているため版を合わせられる）。pure Rust |
| ファイルは DataFusion に読み直させず、表示用に読み込んだデータを登録する | 表示と SQL で列の型がずれない。ファイルを二重に読まない。列はコピーせず共有する |
| 補完は既存のカタログの仕組みに、LocalSource を差し込んで載せる | 補完・ランキング・ポップアップを作り直さずに済む。将来の Explorer にもローカルのテーブルがそのまま出る |
| 登録と実行を同じスレッドの同じキューで処理する | 「登録してからクエリ」の順序が自然に保たれる |
| Snowflake のテーブルとローカルのテーブルを 1 つの文で混ぜない | 実行先が 1 つに決まらない。混ぜたいときは Snowflake の結果を表示してから、それをローカルで引く |

既知の制約:

- Snowflake の TIMESTAMP / TIME は表示用に文字列へ整形してから保持しているので、ローカル SQL では文字列として扱われる
- Snowflake の小さい NUMBER(p, s)（s > 0）は、値を 10^s 倍した整数にスケールを metadata で添えて届く。受け取った時点で Decimal128 に読み替える
- 方言は DataFusion（Snowflake 方言のパーサを指定）。`IFF` や `:` による半構造化データへのアクセスなど、Snowflake 固有の関数・構文の一部は使えない
- 結果は登録したまま保持する。メモリは表示した結果の分だけ増える（上限は後で決める）
